# نموذج الأمان (المرحلة 2)

## 1. طبقات حماية بيانات العيادات

```text
طلب HTTP
  │ 1. Authentication     JWT (HS256, 15 دقيقة) — issuer/audience/lifetime/signature
  │ 2. Tenant             من claim "tid" في الـtoken فقط — لا يُقبل من body/query/header
  │ 3. Permission         [HasPermission("Patients.View")] — صلاحيات العيادة تتطلب جلسة عيادة
  │ 4. Ownership          Global query filter: TenantId = @current  → مورد عيادة أخرى = 404
  │ 5. Business rules     Application services
  ▼
SaveChanges guard        يفرض TenantId عند الإضافة، يرفض تعديل/حذف صف من عيادة أخرى أو بدون نطاق عيادة
  ▼
TenantId في WHERE        TenantId مُعلَّم concurrency token لكل كيان ITenantOwned: كل UPDATE/DELETE يصبح
                         WHERE Id = @id AND TenantId = @current — قيمة TenantId المخزنة في القاعدة هي مصدر الحقيقة،
                         لا الكيان القادم من الطلب. كيان مزوّر بـId عيادة أخرى يؤثر على 0 صفوف → 404 (عزل) لا 409
  ▼
SQL Server               FK مركّب (TenantId, Id) يرفض أي مرجع بين عيادتين حتى عبر SQL خام
```

كل طبقة مُختبرة بشكل مستقل في `backend/tests/ClinicSaaS.IntegrationTests/TenantIsolationTests.cs`
و`ClinicalRecordsIsolationTests.cs`، وتم التحقق من أن الاختبارات تفشل فعلاً عند تعطيل الفلتر أو شرط `TenantId` في
الـWHERE (mutation check).

**ثغرة مُكتشفة ومُصلحة (2026-10-06):** قبل إضافة شرط `TenantId` إلى الـWHERE، كان الحاجز يقارن `TenantId` الأصلي
**كما يراه EF** بالعيادة الحالية. لكيان لم يُحمَّل من القاعدة (مبني من مدخلات الطلب ثم `Attach/Update/Remove`) تكون هذه القيمة
من المهاجم، وكان الـSQL يُحدِّث بالـ`Id` فقط. النتيجة المُثبتة باختبار: عيادة B تستبدل سجل مرفق لعيادة A وتنقله لنفسها
(الكيانات بلا `rowversion` أو FK أب يحميها). لا يوجد endpoint حالي يبني كيانات من المدخلات، لكن الحماية الآن في طبقة البيانات
لكل الكيانات.

## 2. المصادقة

| الضابط | التنفيذ |
|---|---|
| تخزين كلمات المرور | PBKDF2-HMAC-SHA512 (100k) من ASP.NET Core Identity |
| سياسة كلمة المرور | 10–128 حرفاً، حرف + رقم (NIST 800-63B: الطول قبل التعقيد) |
| القفل | 5 محاولات فاشلة → قفل 15 دقيقة (قابل للضبط)، مخزّن في DB فيعمل عبر عدة نسخ من الخادم |
| تعداد الحسابات | نفس الرسالة والكود للبريد غير الموجود ولكلمة المرور الخاطئة + توقيت متساوٍ (hash وهمي)؛ نسيت كلمة المرور يرد 202 دائماً |
| Access token | 15 دقيقة، في الذاكرة لدى الواجهة فقط. **يُفحص في كل طلب أن جلسته (`sid` = عائلة الـrefresh) ما زالت حيّة** (GD-03، المرحلة 3A): الخروج وتغيير/إعادة تعيين كلمة المرور وإنهاء جلسة وتبديل العيادة وإيقاف العيادة أو العضو وإعادة استخدام refresh قديم كلها تُبطل الـaccess token في الطلب التالي (401 `UNAUTHORIZED`) لتوكن العيادة والمنصة معاً. الفحص استعلام واحد على فهارس موجودة (`RefreshTokens.FamilyId`) مدمج مع فحص العضوية (GD-02). على المسارات العامة (`[AllowAnonymous]`) تُعامل جلسة منتهية كأنها بلا token (لا تمنع تسجيل الدخول ولا تصلح هوية لقبول دعوة) |
| Refresh token | عشوائي 256-bit، يُخزن hash فقط، تدوير مع كل استخدام، **إعادة استخدام token قديم تُبطل العائلة كاملة** |
| تخزين الـRefresh في الويب | Cookie `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth` — لا يصل لـJavaScript |
| تطبيقات الجوال | `X-Client-Type: mobile` → الـrefresh في الـbody لتخزينه في Keychain/Keystore، ويُقدَّم في الـbody أيضاً. لا يوجد تطبيق جوال في المستودع اليوم (الوضع موثّق ومغطى بالاختبارات فقط) |
| فصل المتصفح عن وضع الجوال (P3-SEC-08، المرحلة 3A) | أي طلب فيه `X-Client-Type: mobile` **ويبدو من متصفح** (يحمل `Origin` أو أي `Sec-Fetch-*`، وهي رؤوس يضيفها المتصفح ولا تستطيع سكربتات الصفحة ضبطها أو حذفها) يُرفض بـ403 `CLIENT_TYPE_NOT_ALLOWED` قبل أي أثر (لا تدوير ولا جلسة جديدة). وCORS لم يعد يسمح بالرأس `X-Client-Type` فيفشل الـpreflight أصلاً. وفي وضع الويب لا يُقبل refresh إلا من الـcookie (الـbody يُتجاهل). النتيجة: سكربت XSS في الواجهة لا يستطيع الحصول على refresh token طويل العمر (يبقى قادراً على العمل باسم المستخدم ما دامت الصفحة مفتوحة، وهذا مدى أي نظام مبني على cookie). CSP طبقة إضافية وليست الحد الأمني |
| CSRF لنقطتَي الـcookie (المرحلة 3B) | `/auth/refresh` و`/auth/logout` تُصادَق بالـcookie لا بالـbearer: إضافةً إلى `SameSite=Strict` يُرفض (403 `FORBIDDEN`) أي طلب متصفح يحمل `Origin` ليس ضمن `Cors:AllowedOrigins` (يمنع نطاقاً فرعياً شقيقاً على نفس الموقع). الطلبات بلا `Origin` (تطبيقات، أدوات) لا تتأثر. نقاط الـbearer لا تحتاج CSRF لأن المتصفح لا يرسل الـtoken تلقائياً |
| فشل-مغلق للإعدادات (المرحلة 3B) | أي بيئة غير Development ومضيف الاختبار الآلي ("Production"، "Staging"، أي اسم آخر، وحتى "Testing" إن كان الـAPI هو الملف التنفيذي) ترفض التشغيل عند إعداد تطويري/اختباري واضح: مفتاح JWT ناقص/قصير/نمطي/مفتاح الاختبار، اتصال SQL بـLocalDB أو بلا تشفير أو بـ`TrustServerCertificate` أو `sa` أو قاعدة تطوير، أصول CORS غير https أو localhost أو `*`، `AllowedHosts=*`، مزوّد بريد ناقص أو DevMailbox، ترحيل تلقائي، حدود معدل بقيم اختبار، أكثر من نسخة API بلا اعتراف صريح، غياب إعداد الوسيط الموثوق، مستوى سجل Debug أو تسجيل الإطار (يطبع الروابط الكاملة). الرسالة تسرد **أسماء المفاتيح فقط** ولا تعرض قيمة. التفاصيل: `docs/operations/deployment-prerequisites.md` |
| الوسيط العكسي وعنوان العميل (المرحلة 3B) | `X-Forwarded-For/Proto` تُقبل **فقط** إذا كان نظير TCP ضمن `ForwardedHeaders:KnownProxies/KnownNetworks` (CIDR؛ النطاقات الشاملة مثل `0.0.0.0/0` مرفوضة)، ويُؤخذ إدخال أقرب وسيط موثوق فقط (`ForwardLimit`) فلا يستطيع العميل اختيار عنوانه؛ أو `NoProxy=true` فتُتجاهل الرؤوس كلياً. يتبعه تحديد المعدل وسجل التدقيق. لا افتراض لأي مزوّد |
| تدوير مفتاح JWT (المرحلة 3B) | `Jwt:PreviousSigningKeys` مفاتيح للتحقق فقط أثناء التدوير (HS256 فقط). الجلسات لا تعتمد على المفتاح (refresh عشوائي مخزّن hash)، فالتدوير لا يُخرج أحداً. الإجراء: `docs/operations/deployment-prerequisites.md` §4 |
| إعادة تعيين كلمة المرور | رابط لمرة واحدة، 30 دقيقة، يُبطل كل الجلسات. **الرمز في الـfragment (`#token=`) لا الـquery** (المرحلة 3B): المتصفح لا يرسله لأي خادم فلا يصل إلى سجلات الوصول للوسيط أو الخادم أو الـReferer، والواجهة تقرأه مرة واحدة وتمسحه من شريط العنوان؛ الـAPI لا تقبله إلا في جسم POST |
| صمود قاعدة البيانات (المرحلة 3B) | إعادة محاولة فتح الاتصال (محاولتان) و`SELECT` بسيط خارج معاملة (3 محاولات) فقط؛ **لا إعادة محاولة تلقائية لأي كتابة أو معاملة** (حجز، وصفة، مريض، إكمال زيارة…). الفشل العابر (قاعدة بيانات، قفل، حوض اتصالات) → 503 `TEMPORARILY_UNAVAILABLE` + `Retry-After: 5` بلا تفاصيل داخلية. الإرسال بالبريد بعد الالتزام best-effort: فشل المزوّد يُسجَّل (الغرض + نطاق المستلم + نوع الاستثناء فقط) ولا يحوّل الطلب إلى 500 |
| تأكيد البريد | رابط لمرة واحدة، 48 ساعة؛ `Auth:RequireConfirmedEmail` لفرضه عند الدخول |
| نفاذ / OTP / SMS | `VerificationPurpose.PhoneVerification/LoginOtp` موجودة في المخطط؛ المزودون في المرحلة 9، ونفاذ كـexternal identity provider يربط `User` بهوية وطنية موثقة دون تغيير نموذج العضويات |

## 3. منع تصعيد الصلاحيات وإدارة الفريق

| القاعدة | السبب |
|---|---|
| لا يمكن لأحد إنشاء/تعديل دور أو إسناده بصلاحيات لا يملكها هو | من يملك `Roles.Manage` فقط لا يستطيع منح نفسه أو غيره `Patients.Delete` |
| دور المالك لا يُعدّل ولا يُسند عبر إدارة الموظفين | نقل الملكية عملية منفصلة ومقصودة |
| لا يمكن للمستخدم تعديل أو إيقاف عضويته بنفسه، ولا تعديل عضوية المالك | منع الإغلاق الذاتي والاستيلاء |
| إيقاف موظف يلغي جلساته في تلك العيادة فوراً، وكل طلب يفحص أن العضوية ما زالت نشطة (GD-02) | الـaccess token الصادر قبل الإيقاف يُرفض في الطلب التالي (401 `NO_ACTIVE_MEMBERSHIP`)؛ استعلام صغير إضافي لكل طلب عيادة |
| إيقاف العيادة من المنصة يسري **فوراً**: كل طلب بـtoken عيادة يُفحص (`TenantAccessMiddleware`) → 403 `TENANT_SUSPENDED`؛ وانتهاء فترة الاشتراك يجعل العيادة للقراءة فقط (403 `SUBSCRIPTION_EXPIRED` على الكتابة) | لا انتظار لانتهاء الـtoken عند الإيقاف؛ السجلات الطبية تبقى قابلة للاطلاع عند انتهاء الاشتراك (Gate C) |
| الدعوة رابط لمرة واحدة (7 أيام) مرتبط بالمقعد (`{membershipId}.{random}`، يُخزَّن hash فقط). المقعد يبقى `Invited` بلا أي وصول حتى القبول؛ صاحب الحساب الموجود يقبل وهو مسجّل الدخول ولا تتغير كلمة مروره عبر الدعوة؛ إعادة تفعيل مقعد موقوف تتطلب قبولاً جديداً | لا كلمات مرور مؤقتة تُرسل بالبريد؛ لا عضوية بدون موافقة صاحب الحساب (T-010 / QA-02) |
| رد `POST /staff` متطابق للبريد المسجل وغير المسجل، والمقعد المعلّق لا يكشف الاسم أو الجوال أو حالة البريد/كلمة المرور أو آخر دخول أو معرّف الحساب، ولا يُبحث عنه بالاسم؛ سجل التدقيق لم يعد يسجّل `newAccount` | منع تعداد الحسابات وكشف بيانات مستخدمي عيادات أخرى (QA-02) |
| تقييد الفروع: العضو المقيّد بفرع لا يرى مواعيد الفروع الأخرى (404) ولا يحجز فيها | `br` claims في الـtoken |
| العضو المقيّد لا يرى طبيباً يعمل في فروع أخرى فقط (404)، ولا يرى ساعات الفروع الأخرى، ولا يعدّل إلا نوافذ فروعه (نوافذ غيره محفوظة)، ولا يعدّل ملف طبيب مشترك أو فرعاً خارج نطاقه ولا ينشئ فروعاً. المرضى والخدمات على مستوى العيادة بقرار المنتج (الخدمات بلا عمود فرع) | قرار F2 (T-011)؛ يحل تعارض CLAUDE.md §6 للأطباء وساعات العمل، والخدمات تبقى تعارضاً موثقاً حتى قرار مخطط |
| مدير الموظفين المقيّد بفروع لا يمنح إلا فروعه (لا "كل الفروع")، ولا يدير عضواً يتجاوز وصوله فروعه؛ وتغيير فروع عضو يتطلب امتلاك كل صلاحياته مثل الإيقاف | منع تصعيد الوصول عبر الفروع (T-009 / QA-01، QA-04) |
| الطبيب (مقعد له ملف طبيب) يرى ويسجّل زياراته ووصفاته فقط ما لم يملك `MedicalRecords.ViewAllDoctors` (سجلات غيره 404)؛ قراءة الوصفات تتطلب `MedicalRecords.View` | تقليل الوصول للبيانات الطبية حسب الحاجة (T-012). ملاحظة: أدوار العيادات الحالية المخزّنة لا تكتسب الصلاحية الجديدة بدون تغيير بيانات |
| تسجيل الزيارة وتعديلها وإكمالها للطبيب المعالج وحده (GD-01)؛ `ViewAllDoctors` للقراءة فقط | التوثيق السريري يظهر باسم طبيب الزيارة، فلا يكتبه غيره (مدير، مالك، طبيب آخر) → 403 `VISIT_NOT_TREATING_DOCTOR` |
| إكمال الزيارة (`POST /visits/{id}/complete`) يتطلب `Visits.Edit` + `MedicalRecords.Edit`، ونفس قواعد الرؤية (عيادة/فرع/الطبيب نفسه → 404). يُغلق الموعد المرتبط `CheckedIn → Completed` **دون** اشتراط `Appointments.CheckIn` | الإكمال يقفل المحتوى السريري نهائياً، فيُحصر فيمن يملك كتابته (الطبيب)، لا في من يعدّل البيانات الإدارية فقط. إغلاق الموعد هنا جزء من إغلاق اللقاء السريري نفسه وليس إجراء استقبال مستقلاً: الصلاحية الأقوى (`MedicalRecords.Edit`) على زيارة مرئية مرتبطة بهذا الموعد تحديداً تكفي، والانتقال يمر بقواعد `Appointment.TransitionTo` نفسها (لا يمكن إكمال موعد ملغى أو غير محضور)، ولا يمنح أي وصول لمواعيد أخرى. المعاملة واحدة مع قفل لكل زيارة (T-013b) |
| الجلسات: `sid` في الـtoken، عرض الأجهزة وإنهاؤها، تغيير كلمة المرور ينهي كل الجلسات | إنهاء الجلسة يسري على الـaccess token فوراً (GD-03). إيقاف العيادة يُنهي كل جلساتها، **وإعادة تفعيلها لا تُعيد تلك الجلسات** (GD-15): يلزم تسجيل دخول جديد. العضو الموقوف تنتهي جلسته في تلك العيادة أيضاً (يسجّل دخولاً من جديد للوصول إلى عيادته الأخرى) |
| Super Admin بلا جلسة عيادة → لا يصل لبيانات المرضى؛ وتوكن العيادة لا يصل لـ`/platform` | فصل كامل بين صلاحيات المنصة والعيادة: الـtoken يحمل مستوى واحداً فقط. جلسة العيادة لا تُصدر بصلاحيات `Platform.*` أبداً، و`PermissionHandler` يرفض أي صلاحية منصة مع `tid` (دفاع في العمق). مستخدم المنصة الذي يدخل بدون `tenantId` يحصل دائماً على جلسة منصة ولا يُدخل تلقائياً إلى عيادته؛ لدخول عيادة يرسل `tenantId` أو يستخدم `switch-tenant` (T-008 / QA-03) |

## 4. محايدة الثقافة (Culture)

الـAPI يعمل بـ`InvariantCulture` دائماً. على خادم إعداداته `ar-SA` يتحول التقويم الافتراضي إلى الهجري (أم القرى)،
فيُنسَّق `2026-10-08` كـ`1448-04-27` بصمت — اكتُشف هذا أثناء الاختبارات. التواريخ تُخزن وتُنقل ميلادية بصيغة ISO،
والعرض الهجري مسؤولية الواجهة بشكل صريح.

## 5. Rate limiting

| السياسة | الحد الافتراضي | النقاط |
|---|---|---|
| `auth` | 10/دقيقة لكل IP | login, register, refresh |
| `sensitive` | 5/15 دقيقة لكل IP | forgot/reset password, verify/resend email (وOTP لاحقاً) |
| عام | 300/دقيقة لكل مستخدم (أو IP) | كل الـAPI |

الحدود حالياً داخل العملية (in-process)؛ المرحلة 14 تضيف Redis عند تشغيل أكثر من نسخة.

| # | الثغرة | المعالجة في النظام الجديد |

| S11 | لا security headers | `nosniff`, `DENY`, CSP, `no-referrer`, `no-store`, HSTS خارج التطوير |

## 7. الأسرار

- لا أسرار في Git: `appsettings.json` يحتوي قيماً فارغة.
- أول Super Admin يُنشأ عند التشغيل من `Bootstrap__SuperAdminEmail` و`Bootstrap__SuperAdminPassword` (من مخزن الأسرار)، ثم تُحذف من البيئة. Development يستخدم Windows auth لـLocalDB ومفتاح JWT مؤقت يتولد عند التشغيل.
- الإنتاج: متغيرات بيئة / Secret store (`Jwt__SigningKey`, `ConnectionStrings__Default`).
- السجلات لا تحتوي كلمات مرور أو tokens أو محتوى رسائل البريد (البريد التطويري يُكتب في ملفات `.dev-mailbox/` المستثناة من Git).
